# Levbush Relationships

Бот для группы обсуждения канала: подробная статистика участников и пар, досье и карта связей, которые ведёт
**Qwen 3.8 27B** (звук и видео ему описывает **Nemotron 3 Nano Omni**, речь расшифровывает **Parakeet v3**),
пересказ последних событий, расшифровка голосовых, онлайн-карта (сайт / Mini App).

## Как устроено

```
Telegram ──Bot API──► levbush run (бот: только команды) ─┐
         ──MTProto──► Telethon (твой аккаунт) ───────────┤   история и живой сбор: сообщения, правки, удаления,
                                                          │   реакции поимённо, входы/выходы, профили, медиа
                                                        ▼
                    ~/.local/share/levbush/cache.db (SQLite) + /mnt/shared/levbush/media   ← переписка только локально
                                                        │
             stats.compute (каждые 2 мин) ──────────────┤──► Supabase Postgres: people, stats_*, pair_stats,
             разбор Qwen (первый прогон, потом ежедн.) ──┘    relations, dossiers, episodes
                                                                     │  sql/api.sql — api_graph / api_person / …
                                     Edge Function `api` (подпись Telegram) ◄── сайт web/ (GitHub Pages = Mini App)
```

- **Статистика** (`levbush/stats.py`): на человека — за день/неделю/месяц (последние 30/12/12) и всё время, среднее
  за день с момента вступления: сообщения, ответы, цитаты, комментарии к постам, пересылки, упоминания, реакции
  (поставлено/получено), медиа по типам, кружки и голосовые (и их длительность), стикеры, опросы, ссылки, слова,
  правки. Плюс: первый вход, время в группе с учётом выходов, часы и дни активности, средняя сессия, активных минут
  в день, медианное время ответа, серии дней, начатые беседы, любимые реакции. По парам (кто → кого): ответы, цитаты,
  упоминания, реакции, пересылки. Сила связи = количественная часть (0.4) + оценка нейросети (0.6).
  Боты в статистику не входят (их сообщения остаются в переписке для нейросети как контекст). Сообщения
  «от имени группы/канала» приписываются человеку через `LEVBUSH_ALIASES`. Имена и ники берёт бот
  (`getChatMember`): Telethon для контактов аккаунта отдаёт имена из записной книжки.
- **Разбор** (`levbush/analyze.py`): переписка режется на окна (перерыв ≥ 30 мин или полная смена действующих лиц).
  Шаг = несколько последовательных окон + уже разобранные окна за 48 ч как контекст + текущие досье участников и
  описания связей между ними (с id записей). Этапы прогона: 1) Parakeet v3 расшифровывает речь; 2) Nemotron
  описывает голосовые, кружки, видео, GIF и видеостикеры (файл целиком + расшифровка) — описания в кэше
  (`media_desc`); 3) Qwen получает переписку: фото и PDF-страницы как есть, у видео — 4 кадра и описание Nemotron, у
  голосовых — расшифровку и описание, из текстовых файлов — текст — и возвращает **правки** — `add` / `update` / `remove` записей досье, сводку, поля связи,
  события и заметки о связи (`levbush/dossier.py`). Досье не переписывается целиком и не версионируется: у каждой
  записи видно, с какого числа она известна, когда и как изменилась (со старым текстом) или устарела.
  Первый прогон — такими шагами по всей истории; дальше раз в день (`LEVBUSH_DAILY_AT`) с контекстом за два дня.
  Кроме пишущих, в шаг идут полные досье тех, кого в окнах обсуждают заочно: @упоминание, ответ/цитата на их
  сообщение, пересылка или имя из «Как называют» в досье (с падежами: Лёва → Лёвы, Лёвой; формы вроде «Льва»
  модель вносит сама). Остальные люди группы — одной строкой; им можно только добавлять записи «со слов …».
  Запрос считается точно (`/tokenize` vLLM) и должен влезть в контекст вместе с ответом. Досье идут всегда целиком,
  а ужимается остальное: контекст и подробности связей, затем шаг делится по окнам, затем — число обсуждаемых
  заочно; одно окно, которое всё равно не влезает, разбирается по половинам.
  Досье, переросшее 90 записей или 20 тыс. знаков (`LEVBUSH_DOSSIER_MAX_ENTRIES` / `_CHARS`), Qwen сжимает в
  биографию: сливает повторы, дневниковые мелочи обобщает или выбрасывает (обычно до 40–55 записей). Старые записи
  остаются в `data.archive`.
  Прогресс и примерное оставшееся время — в `/status`, в сообщении админу (обновляется раз в 30 с) и на карте.
- **Почему так** (сравнение на 6 шагах, ~1900 сообщений): Qwen 3.8 27B — 136 записей, 94 % ссылок на сообщения
  самого человека; Nemotron — 10 записей, половина на английском; Gemma 4 26B — точно, но скупо (52 записи, связей
  почти нет); Qwen 3.6 35B — треть ссылок выдумана.
- **Модели** бот поднимает сам, на GPU — одна за раз: Nemotron (`levbush-nemotron`, порт 18090) и Qwen 3.8 27B
  (`levbush-qwen`, 18091; MTP — втрое быстрее; KV TurboQuant k8v4, контекст 176k; с TurboQuant MTP в чистом
  vLLM 0.27.1 портит вывод — нужен `deploy/vllm-0.27.1-turboquant-mtp.patch`, см. ~/CLAUDE.md; 1 слот: с двумя MTP +
  картинки роняют движок, пересказ ждёт конца шага). Гасятся после 15 мин простоя; ждут, пока MiniMax H3 считает запрос; при нехватке VRAM
  усыпляют общий vLLM-Qwen пользователя и будят после.
- **Пересказ** — Qwen: сначала общий сервер пользователя `:8080` (если там есть модель), иначе свой. Nemotron ради
  пересказа не поднимается: картинки, кадры видео, расшифровки и уже готовые описания.
- **Обращение к боту** (`levbush/ask.py`): сообщение в группе, которое **начинается** с `@бота`, — вопрос нейросети
  (сервер — как у пересказа). В запрос идёт хвост переписки до обращения (≤ 12 ч, ≤ 80 сообщений, ~12k токенов;
  `LEVBUSH_ASK_CONTEXT_*`): сообщения самого бота — репликами модели (роль assistant), остальные — строками
  «#id ЧЧ:ММ Имя: текст» от user; картинки и кадры — только у обращения и сообщения, на которое оно отвечает.
  В системном промпте — список людей с досье (имя, ник, id, «Как называют», кратко); полное досье модель
  запрашивает сама инструментом `get_dossier` (до 3 раундов, до 6 человек за раз). Поэтому свой Qwen запускается
  с `--enable-auto-tool-choice --tool-call-parser qwen3_xml`; сервер без инструментов — ответ по списку.
  Ответ бот сразу кладёт в кэш, чтобы следующее обращение видело его как реплику модели.
  Ответ — rich-сообщение (Markdown, формулы LaTeX, спойлеры); все эмодзи заменяются официальными анимированными
  премиум-эмодзи Telegram (`levbush/emoji.py`: наборы `RestrictedEmoji` + `AnimatedEmoji`, ~1700 вариантов, кэш на
  неделю; нужен Premium у владельца бота). Ответ из одного эмодзи уходит отдельным сообщением — крупным.
  Интернет (`levbush/websearch.py`): инструменты `web_search` — свой SearXNG в Docker (`127.0.0.1:8890`, конфиг
  `~/.config/searxng/settings.yml`, JSON включён, лимитер выключен — доступ только локальный) и `web_fetch` — текст
  страницы (trafilatura) или PDF (pdftotext). `web_fetch` ходит только на публичные адреса: адрес хоста проверяется и
  после каждого редиректа (иначе через бота можно было бы прочитать vLLM, Jupyter, роутер). Запуск SearXNG:
  `docker run -d --name searxng --restart unless-stopped -p 127.0.0.1:8890:8080 -v ~/.config/searxng:/etc/searxng
  searxng/searxng`; без него — `LEVBUSH_WEB_SEARCH_URL=` (пусто), и инструменты не предлагаются.
- **Поиск** `/find` (`levbush/search.py`) — по смыслу и по словам во всей истории, тоже только локально:
  `~/.local/share/levbush/search.db` (SQLite): векторы — [sqlite-vec](https://github.com/asg017/sqlite-vec)
  (`vec0`, косинус, перебор в C: 130 тыс. векторов по 1024 — ~0,1 с), слова — FTS5 по основам Snowball
  («поездку» найдёт «поездка»). Отдельный файл, а не таблицы в cache.db: индекс можно удалить и пересобрать,
  а удаление/правка сообщения меняет векторы и FTS одной транзакцией (с FAISS пришлось бы синхронизировать
  отдельный файл индекса). Модель — **jina-embeddings-v5-omni-small-retrieval** (`/mnt/shared/Models/
  jina-v5-omni-small-retrieval`, CC BY-NC 4.0): текстовая башня = jina-embeddings-v5-text-small (Qwen3-0.6B,
  MMTEB 67,7, русский), картинки — в том же пространстве, так что текстовый запрос находит и фото. Считает отдельный
  процесс системного python3 (`levbush/embed_worker.py`, как Parakeet): torch не грузится в бота.
  - **Что в индексе**: документ сообщения — текст + опрос / превью ссылки / имя файла + расшифровка Parakeet +
    описание Nemotron (голосовые, кружки, видео, GIF) + текст из текстовых файлов. Короткое (< 12 букв: «да»,
    «ахах») — только по словам: вектор у него шумный. Фото и картинки-файлы — отдельным вектором картинки
    (стикеры — нет: тысячи одинаковых). Служебные — нет, боты — да (в выдаче «[бот]»).
  - **Правки и удаления**: у сообщения «штамп» (правка, состояние медиа, расшифровка, описание, длина текста);
    изменился — документ пересобирается, вектор пересчитывается; удалённое убирается сразу. Полнотекстовая часть
    догоняет кэш раз в 5 мин (`LEVBUSH_SEARCH_INTERVAL`) и перед `/find` (вся история — ~6 с, дальше ~0,3 с).
  - **Векторы**: первичная индексация всей истории (~130 тыс. текстов и ~7,3 тыс. фото) сама не запускается —
    `/index run [cpu|gpu]` (или `levbush index`). Дальше новые сообщения досчитываются в фоне (если очередь ≤
    `LEVBUSH_SEARCH_AUTO_MAX`), по умолчанию на CPU. GPU — только когда там нет модели бота, не идёт генерация H3
    и свободно ≥ 6 ГиБ; модель бота, собравшаяся запуститься, забирает GPU: индексация между пачками переезжает на
    CPU (`LLMManager.gpu_guests`). Время: CPU, 8 потоков — ~25–33 текста/с и ~4 с на фото (вся история: ~1,5 ч
    текстов + ~8 ч фото; 20 потоков — ~50 текстов/с, 2,3 с на фото); GPU (оценка, не мерили) — ~10 мин,
    ~3–5 ГиБ VRAM (1,8 ГБ весов bf16 + активации). ОЗУ процесса на CPU — до 5,5 ГБ. Модели для запросов — CPU,
    ~0,1–0,3 с на запрос (первый — плюс загрузка ~3 с), гасится после 15 мин простоя.
  - **Выдача**: RRF по трём спискам (вектор текста, вектор картинки ×0,8, FTS), с порогом косинуса
    (текст 0,25, фото 0,22 — у случайных фото 0,15–0,2); в запросе «фото/скрин/картинка …» эти слова не ищутся в
    тексте, а вес картинок ×1,5; альбом — одной строкой. На строку — ссылка на сообщение
    «Имя · дата», значок вложения и фрагмент с найденными словами жирным; по 7 на страницу, кнопка «Ещё».

## Запуск

1. **Бот**: @BotFather → новый бот. Добавить в группу обычным участником (права админа и выключенный privacy mode
   не нужны — всё собирает Telethon; команды бот видит и так).
   Для входа на сайте — `/setdomain` → `egoriumas.github.io`; для Mini App — `/newapp` (URL сайта).
2. **Telethon**: my.telegram.org → API development tools → `api_id`, `api_hash`.
3. **База**: Supabase, проект `levbush-relationships` уже создан, схема и Edge Function задеплоены.
   Нужна строка подключения: Connect → **Transaction pooler** (порт 6543 — 5432 через VPN sbx не проходит)
   (пароль — «Reset database password»).
4. Настройки: `cp deploy/levbush.env.example ~/.config/levbush.env && chmod 600 ~/.config/levbush.env`, заполнить.
5. Вход Telethon (интерактивно, один раз): `~/.local/share/levbush/venv/bin/python -m levbush login`
6. Сайт: в `web/config.js` — `bot: "<имя бота без @>"`; опубликовать `web/` на GitHub Pages.
7. Сервис:
   ```bash
   ln -s ~/levbush_relationships/deploy/levbush.service ~/.config/systemd/user/levbush.service
   systemctl --user daemon-reload && systemctl --user enable --now levbush
   journalctl --user -u levbush -f
   ```
8. В личке боту (от `LEVBUSH_ADMIN_ID`): **`/initiate`** — только после этого начинается сбор: участники →
   вся история → реакции поимённо → профили → медиа, дальше — живой сбор. Затем бот выгружает статистику и
   спрашивает, запускать ли первый разбор нейросетью. Флаг сохраняется: после перезапуска сбор продолжается сам.

Telegram-лимиты: паузы `LEVBUSH_TG_HISTORY_DELAY` (1 с на 100 сообщений), `TG_REACTION_DELAY` (1,5 с),
`TG_MEDIA_DELAY` (0,7 с), `TG_PROFILE_DELAY` (2 с); FloodWait — ждём +10 % и замедляемся вдвое (до ×16),
через 30 мин без FloodWait темп восстанавливается. Счётчик FloodWait и текущий темп — в `/status`.

## Команды бота

`/stats [@ник]` (или ответом) · `/me` · `/top [метрика] [d|w|m|a]` · `/pair @a [@b]` · `/dossier [@ник]` ·
`/links [@ник]` · `/retell 2ч | 30м | 14:30 | вчера 20:00` (или ответом на сообщение; не дальше 48 ч) · `/map` ·
`/text` (ответом на голосовое или кружок — расшифровка Parakeet; в личке достаточно прислать голосовое) ·
`/find о чём` — поиск по истории (фильтры: `@ник` или `от:Имя`, `за:05.2026` / `за:вчера` / `за:неделю`,
`с:01.05 по:20.06`, `"точная фраза"`; ответом на сообщение без слов — похожие на него).
Админ: `/initiate`, `/status`, `/analyze` (`/analyze stop` — остановить), `/describe` (описать новые видео и голосовые Nemotron'ом сейчас), `/sync`,
`/index` (индекс поиска; `/index run [cpu|gpu]` — посчитать векторы, первый раз — вся история; `/index stop`),
`/maintenance`, `/qwen` (состояние своего Qwen; `/qwen stop` — погасить сразу, не дожидаясь 15 мин простоя;
занят разбором или запросом — `/qwen stop force`). В группе: `@бот вопрос` — разговор с нейросетью. Доступ — участникам группы.

## CLI

`python -m levbush login | run | sync | stats | analyze | migrate | web | status | index | find` (подробности — `--help`).
`levbush index --device cpu --threads 16 [--no-images]` — векторы из консоли (бот может работать: замок
`search.lock`, фоновая дозаливка бота подождёт); `levbush find "запрос @ник за:05.2026"` — выдача в консоль.
Модель: `HF_HUB_DISABLE_XET=1 hf download jinaai/jina-embeddings-v5-omni-small-retrieval --revision e3ae4b6e4af4ec0799cd931aefaff03235b5f9d4
--local-dir /mnt/shared/Models/jina-v5-omni-small-retrieval`; пакеты бота — `sqlite-vec`, `snowballstemmer`.

## Этап 2: без Supabase

Локальный Postgres → `LEVBUSH_DATABASE_URL` на него → `levbush migrate` → `levbush web --port 8095`
(тот же API на `/api` + раздача `web/`, TLS через Caddy) → в `web/config.js` `api: "/api"`.
